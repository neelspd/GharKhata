# GharKhata — Architecture Notes

## Architecture Philosophy

GharKhata begins as a **modular monolith**.

Simple enough to build quickly. Structured enough to grow into a serious ledger system. Split into services only when there is real, measured pressure to do so.

## Database Design

PostgreSQL, schema-per-tenant.

- `config` schema: tenants, users, refresh tokens (shared, one per database)
- `tenant_<name>` schema: the actual ledger (one per household, provisioned at signup)

JSONB used on `entries.metadata` for category-specific detail that doesn't need to be queried relationally (e.g. milk type, laundry item breakdown). Core financial fields (amount, date, vendor) stay as typed columns.

---

## Core Entities

### Tenant (Household)

One household = one Postgres schema. Isolation is strong, migrations run per-schema.

### User

Belongs to exactly one tenant. Role: ADMIN or MEMBER. OAuth provider folded into the users table (one provider per user). Password and OAuth are mutually non-exclusive — the DB enforces at least one login method.

### Vendor

A named person, shop, or service provider connected to the household.
Examples: Ramesh Dairy, Suresh Laundry, Kamla Bai (maid).

Every recurring service connects to a vendor. Settlement is vendor-wise.

### Category

Config-driven, data not code. Each category has a type:
- `QUANTITY_RATE` — Milk, Laundry (quantity × rate = amount)
- `VARIABLE_AMOUNT` — Vegetables, Groceries (amount entered directly)
- `FIXED_MONTHLY` — Newspaper, House Help Salary (fixed amount per month)

### Unit / Category-Unit

Units (L, KG, PKT, DZ, PCS) are a shared master. A category can support multiple units, each with its own rate (or no rate for variable-amount categories). Same unit can price differently per category.

### Entry (append-only)

**Entries are never UPDATEd or DELETEd.**

Every diary entry is an immutable event row. Corrections post a new `EntryCorrected` event referencing the original via `correction_of`. The original row stays in the log forever — matching how a physical diary works (cross out, write below, never erase).

This means: no `PATCH /entries/:id`, no `DELETE /entries/:id`. These routes do not exist.

### Ledger Entry (derived)

Every entry produces a balanced debit/credit pair in the `ledger_entries` table — proper double-entry bookkeeping. A constraint trigger (deferrable, fires at COMMIT) rejects any write that leaves the books unbalanced. Corrections reverse the original pair (flag `reversed = TRUE`) and post fresh rows; original rows are never touched.

### Payment

Money paid to a vendor against their running balance. Posted as its own record, not an edit to any entry.

### Statement (monthly close)

Per-vendor monthly settlement, moving through a state machine:

```text
DRAFT → REVIEWED → CLOSED → PAID
```

Each vendor's statement advances independently. Milk can be PAID while Laundry is still DRAFT.

### Recurring Rule *(v0.2)*

Predictable entries (daily milk, monthly salary) auto-generated by a background worker. Not in v0.1 — entries are manual in the first version.

## Entry Model

```text
id              BIGSERIAL
event_id        UUID (unique)
sequence_no     BIGSERIAL
aggregate_id    UUID            -- shared across an entry and its corrections
event_type      TEXT            -- 'EntryRecorded' | 'EntryCorrected'
category_code   TEXT
vendor_id       UUID
occurred_on     DATE
unit_code       TEXT
quantity        NUMERIC(10,2)
amount          NUMERIC(12,2)   -- always stored; computed from qty×rate or entered directly
note            TEXT
correction_of   UUID            -- event_id of the row being corrected, NULL for originals
entered_by      UUID            -- user id
recorded_at     TIMESTAMPTZ
metadata        JSONB           -- category-specific detail
```

Note: no `updated_at`. Append-only rows are never updated — `recorded_at` is the only timestamp needed.

Example `metadata` for milk:

```json
{
  "milk_type": "cow",
  "delivery_status": "delivered"
}
```

Example `metadata` for laundry:

```json
{
  "items": [
    { "name": "shirt", "qty": 3, "rate": 15 },
    { "name": "pant", "qty": 2, "rate": 20 }
  ],
  "return_status": "pending"
}
```

## Settlement Query

```sql
SELECT
  v.id AS vendor_id,
  v.name AS vendor_name,
  SUM(e.amount) AS total_amount,
  COALESCE(SUM(p.amount), 0) AS paid_amount,
  SUM(e.amount) - COALESCE(SUM(p.amount), 0) AS balance
FROM entries e
JOIN vendors v ON v.id = e.vendor_id
LEFT JOIN payments p
  ON p.vendor_id = e.vendor_id
  AND p.paid_on >= :month_start
  AND p.paid_on < :next_month
WHERE e.occurred_on >= :month_start
  AND e.occurred_on < :next_month
  AND e.event_type = 'EntryRecorded'   -- only the originals
  AND e.event_id NOT IN (              -- exclude entries that have been corrected
      SELECT correction_of FROM entries WHERE correction_of IS NOT NULL
  )
GROUP BY v.id, v.name;
```

## API Endpoints

```text
POST   /entries                        ← record a new diary entry
POST   /entries/correct                ← post a correction (never edits the original)
GET    /entries/day/{date}             ← full detail for one diary day (with event IDs for corrections)
GET    /entries/{aggregate_id}/history ← full audit trail for one entry

POST   /vendors
GET    /vendors
GET    /vendors/{vendor_id}
PATCH  /vendors/{vendor_id}

POST   /payments
GET    /payments?vendor_id=&month=

GET    /statements/{month}
POST   /statements/{month}/{vendor_id}/review
POST   /statements/{month}/{vendor_id}/close
POST   /statements/{month}/{vendor_id}/pay

GET    /dashboard/calendar/{month}
GET    /dashboard/summary/{month}
GET    /dashboard/trend/{category_code}

GET    /categories
POST   /categories
```
